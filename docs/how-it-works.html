1 · Por fuera — la vista del usuario

Tres comandos son los que vas a usar el 99% del tiempo:

$ # 1. Decir qué pipeline ejecutar y con qué input
pq add examples/youtube-video --input topic="IA en 2026"

# 2. Arrancar el worker en foreground (Ctrl+C = parada limpia)
pq daemon

# 3. Inspeccionar lo que pasa
pq list
pq logs 1
pq cancel 5
pq retry 7

Detrás de esos cuatro verbos hay una única tabla SQLite (runs) y una única carpeta (runs/<id>/meta.json) que persiste el estado entre reinicios. La CLI no es más que una forma de manipular esa tabla.

Lo que cada comando hace a alto nivel

ComandoEfecto en la DBEfecto en disco
pq add INSERT en runs (status=queued) + INSERT en steps (uno por step) Escribe runs/<id>/meta.json con el snapshot del YAML
pq daemon UPDATE status a running/done/failed/waiting/cancelled Ejecuta los command de cada step con cwd=pipeline_dir
pq listSELECT (solo lectura)—
pq logsSELECTLee runs/<id>/steps/<step>/log.txt
pq retry UPDATE runs status=queued, UPDATE steps status=pending—
pq cancel UPDATE runs a cancelled, UPDATE steps a failed Lee meta.json["pid"] y manda SIGKILL

Y, si configuras [scheduler] cycle_pipelines en el config.toml, pq daemon también escribe por su cuenta en runs — eso es lo que llamamos el ciclo automático.

2 · Por fuera — lo que se crea en disco

Toda la información persistente vive bajo data_dir. Si usas --data-dir ~/.local/share/pq, ahí encuentras:

~/.local/share/pq/ # raíz de toda la cola ├── pq.db # una sola DB SQLite global: tabla runs + steps + counters ├── runs/ # un directorio por run (id numérico) │ └── 1/ # el run id=1 │ ├── meta.json # snapshot del YAML + pid vivo del subprocess, si lo hay │ └── steps/ │ └── guion/ │ └── log.txt # stdout/stderr del step ├── db/ # una DB SQLite por pipeline_name (memoria persistente) │ ├── youtube-video.db # expuesta al step como $PQ_DB_PATH │ └── podcast.db

Lo importante: meta.json contiene la copia congelada del pipeline.yaml en el momento de hacer add. El worker nunca relee el YAML de disco. Si editas el YAML después de encolar, ese cambio no afecta al run en curso.

Y las runs/<id>/steps/<step_id>/log.txt — los outputs nativos de cada step — son paths dentro del pipeline_dir, no dentro de data_dir. La estructura runs/<id>/steps/... es solo para logs y metadatos; los outputs reales (imágenes, mp4, txt) viven junto al pipeline en examples/youtube-video/outputs/....

4 · Por dentro — el flujo de pq add

Cuando haces pq add examples/youtube-video --input topic="...", el código hace esto, en orden:

cli.add_cmd ├─load_pipeline pq/pipelines.py │ └─ parsea pipeline.yaml → dataclass Pipeline ├─validate_pipeline pq/pipelines.py │ └─ 3-color DFS: detecta ciclos en `needs`, también mutual exclusion count/count_from ├─parse --input key=val (validación local en cli.py) ├─init_db pq/db.py (idempotente) ├─SELECT finished_at FROM runs WHERE pipeline_name=? AND status='done' │ └─ para calcular cooldown_until ├─INSERT runs (pipeline_name, pipeline_dir, inputs_json, status='queued', cooldown_until) ├─ por cada step: INSERT steps (run_id, step_id, ...) ├─ escribir runs/<id>/meta.json con snapshot del YAML (read one more time de disco) └─ensure_pipeline_db pq/pipeline_db.py → data_dir/db/<name>.db

Lo que NO hace (y eso es lo importante):

  • No crea el subprocess. No ejecuta nada. Solo deja una fila queued en la tabla.
  • No relee meta.json para nada — solo lo escribe.
  • Si el pipeline dir tiene archivos en produces que ya existen, NO los cuenta como "skip". El skip-if-exists lo decide el worker al ejecutar cada step.

5 · Por dentro — el bucle del daemon

Esto es el corazón. worker_loop es un while infinito que cada iteración intenta tres cosas, en este orden de preferencia:

worker_loop(cfg, stop): ┌─loop while not stop.should_stop (con first_iteration para garantizar 1 vuelta)──┐ │ │ │ A. run_id = scheduler.pick_next_run(conn, now, quota, today) │ │ └─ SELECT runs WHERE status IN (queued, waiting) ORDER BY id ASC │ │ └─ filtra por cooldown_until <= now │ │ └─ filtra por quota si tiene step upload │ │ │ │ ¿A devolvió un id? ─────sí──→ _execute_run(run_id) │ │ └─ subprocess por step │ │ └─ UPDATE runs status, etc. │ │ └─ continue (vuelve al inicio del loop) │ │ │ │ B. picked = cycle.next_due_pipeline(cycle_pipelines, ...) [solo si A=None]│ │ └─ recorre cycle_pipelines desde cycle_idx (en memoria) │ │ └─ para cada uno mira: │ │ ├─ hay runs previos? │ │ ├─ el último está 'done'? │ │ ├─ cooldown_until <= now? │ │ └─ quota diaria OK si tiene upload step? │ │ └─ devuelve (next_idx, pipeline_name) del primero "due" │ │ │ │ ¿B devolvió algo? ────sí──→ enqueue_cycle_run(pipeline_name) │ │ └─ escribe run queued en DB │ │ └─ continue (NO ejecuta en este loop) │ │ │ │ C. nada: sleep poll_interval_seconds │ │ │ └────────────────────────────────────────────────────────────────────────────┘

La regla invisible que lo une todo: todas las fuentes de runs (manual add, auto-enqueue del ciclo) terminan escribiendo en la misma tabla runs con status='queued' + INSERT id. El ORDER BY id ASC del pick_next_run garantiza FIFO absoluto — el que llegó antes, sale primero. No hay "run auto con prioridad" ni "run manual preferente".

Una vuelta del loop, paso a paso

  1. abrir conexión a data_dir/pq.db.
  2. calcular now y today (today en zona horaria del config).
  3. intentar A: pick_next_run. Si encuentra algo, ejecuta y continue.
  4. intentar B: si no había nada encolado, mirar el ciclo. Si toca, encolar y continue — la siguiente iteración verá el run nuevo y lo cogerá por A.
  5. intentar C: si nada, dormir poll_interval_seconds.
  6. cerrar conexión y volver al while.

¿Por qué el ciclo encola en una iteración y ejecuta en la siguiente? Por FIFO. Si el ciclo ejecutara inline, cualquier pq add que llegase entre A y la ejecución del run auto se saltaría. Haciendo continue, la siguiente iteración pasa por A de nuevo y el motor FIFO decide.

6 · Por dentro — la lógica del ciclo

El ciclo no es más que un índice entero que rota por una tupla de nombres. Lo importante es que ese índice vive en la memoria del proceso del daemon; no se persiste en la DB.

EstadoDónde viveSobrevive a restart
cycle_idx (siguiente pipeline a despachar) variable local en worker_loopNO — vuelve a 0
cooldown_until del último run columna runs.cooldown_untilsí
cuenta de uploads del día tabla counterssí
lista cycle_pipelines config.tomlsí

Después de un SIGKILL del daemon, el siguiente arranque empieza en 0 y puede que re-despache el mismo pipeline que acababa de terminar. Pero si su cooldown dice "espera 4h", el ciclo lo va a saltar y pasará al siguiente. El cooldown es la verdad; cycle_idx es solo una pista de fairness.

Cómo decide next_due_pipeline si un pipeline toca

función _pipeline_name_is_due(conn, name, today, max_uploads, now): 1. SELECT id, pipeline_dir, cooldown_until, status FROM runs WHERE pipeline_name=? ORDER BY id DESC LIMIT 1 2. si no hay rows → DUE (primera vez) 3. si el último status NO es 'done' (sigue running / waiting / etc.) → NO DUE: previous run still active 4. si cooldown_until > now → NO DUE: cooldown active 5. si get_uploads_today >= max Y el pipeline tiene algún step upload → NO DUE: daily upload quota full 6. sino → DUE

Detalle no obvio: el check de quota (paso 5) es defensivo. Un pipeline sin steps upload nunca va a ser bloqueado por la quota de uploads, aunque la quota esté llena. Eso es lo que queremos: que los pipelines que no suben sigan corriendo aunque YouTube ya tenga su ración diaria.

7 · Por dentro — qué pasa cuando ejecuta un step

Una vez que worker_loop tiene un run_id (venga de A o de B), _execute_run hace:

_execute_run(conn, run_id): 1. leer runs/<id>/meta.json (snapshot + pipeline_dir) 2. reconstruir Pipeline desde el snapshot con _pipeline_from_snapshot 3. calcular orden topológico desde `needs` con _topo_order_from_snapshot 4. UPDATE runs SET status='running', started_at=now 5. commit 6. para cada step en orden topológico: ├─ si el step es type='upload' y quota llena → │ UPDATE runs SET status='waiting', commit, return (pausa el run) ├─ UPDATE steps SET status='running', commit ├─ runner.run_step_with_retries(...) ← hace lo siguiente: │ ├─ ¿outputs ya existen? (skip-if-exists, mira disco en pipeline_dir) │ │ └─ sí → StepResult(status='skipped'), sin subprocess │ ├─ abrir subprocess.Popen con env vars: │ │ PQ_RUN_ID, PQ_PIPELINE_DIR, PQ_INPUT_<KEY>, PQ_DB_PATH │ ├─ escribir pid en meta.json (read-modify-write, preserva otras keys) │ ├─ proc.wait() interrumpible por _wait_or_stop(stop, ...) │ └─ (finally) limpiar pid de meta.json ├─ si status='done' o 'skipped' → │ UPDATE steps SET status='done' │ si type='upload' → counter.mark_upload_done (++) ├─ si status='failed' → │ UPDATE steps SET status='failed', failed=True, break └─ commit 7. UPDATE runs SET status='done'|'failed', finished_at=now si done Y cooldown > 0 → UPDATE runs SET cooldown_until=finished+cd

La regla de oro del skip-if-exists: se mira UNA vez antes del loop de iteraciones, no por iteración. Tres ramas distintas según qué defina el step:

  • step.iterates is None → chequea cada step.produces directamente contra disco.
  • step.iterates.count is not None → chequea todos los iteration.substituted_outputs.
  • step.iterates.count_from is not None → chequea cada archivo matched tiene su output derivado.

8 · Casos raros / conflictos

Caso 1 · haces pq add mientras el ciclo está auto-encolando

Lo que pasa: ambos terminan escribiendo filas queued en la misma tabla. La inserción es atómica (SQLite), no hay race. El id mayor corresponde al insert más reciente. pick_next_run ordena por id ASC, así que el viejo gana. Si justo el worker está entre "no hay cola" y "voy a auto-encolar", tu add entra antes y el ciclo encola otro después, pero ambos pasan por A en orden FIFO.

Caso 2 · quota llena, un pipeline del ciclo toca

Si pipeline_A del ciclo tocó (cooldown listo) pero el contador de uploads ya está en el máximo, A queda bloqueado. El ciclo pasa al siguiente: B. Pero B no tiene steps upload → quota no le afecta, se ejecuta. Cuando termina B, el contador sigue lleno, así que A sigue esperando. La cuota es global, no por pipeline.

Caso 3 · falla un step → ¿se reintenta en la misma vuelta?

No. _execute_run marca el run como failed en cuanto cualquier step falla. El siguiente intento del pipeline ocurre en la siguiente vuelta del ciclo, no inmediatamente. Si quieres reintentar YA, usa pq retry que cambia el status a queued y el worker lo coge por FIFO en la siguiente iteración de A.

Caso 4 · SIGINT durante un step, SIGINT durante cooldown (backoff)

Si pulsas Ctrl+C mientras un step corre, el handler setea stop.should_stop. proc.wait() no es interrumpible, pero _execute_run lo deja terminar (SIGINT del SO al daemon no mata al subprocess). Luego while not stop.should_stop sale. Para abortar YA, usa pq cancel <id> — ese sí manda SIGKILL directo al PID guardado en meta.json.

Caso 5 · daemon se cae a mitad de un run

El step subprocess queda huérfano si el daemon muere con SIGKILL. La fila en DB queda en running para siempre. Esto NO lo detecta el sistema hoy. La solución práctica: mata el subprocess a mano o usa pq retry después de matar al huérfano. (Y mira si quieres añadir un "sweep stale runs on startup" en un futuro, hoy no está.)

Caso 6 · edito el pipeline.yaml después de hacer pq add

El snapshot en runs/<id>/meta.json se congela en el momento del add. El worker lee del snapshot, no del YAML en disco. Tu cambio no afecta a ese run. Para la siguiente vuelta del ciclo, el worker usa resolve_pipeline_dir (lee de la DB, no del YAML) y luego load_pipeline — ahí sí relee el YAML en disco. Así que una edición se aplica a partir del siguiente run del ciclo, no al run en curso.

Caso 7 · cancel sobre un run auto-encolado por el ciclo

Igual que cualquier otro run: cancel lee meta.json["pid"], SIGKILL, marca cancelled. Funciona idéntico. No hay nada especial.

9 · Veredicto — ¿está bien lo que hiciste?

Recap rápido de lo que sí funciona y lo que tiene zonas grises:

Comportamiento prometidoImplementación realVeredicto
FIFO estricto multi-pipeline pick_next_run con ORDER BY id ASC, todas las fuentes de runs comparten la misma tabla OK
Cooldown por pipeline cooldown_until en DB, checked en _execute_run al terminar y en pick_next_run al elegir OK
Quota diaria de uploads counters en DB, checkeada en pick_next_run y en cada step upload OK
Skip-if-exists idempotencia Tres ramas en runner según iterates; se chequea una vez por step antes del loop OK
SIGKILL mediante cancel Runner escribe pid a meta.json antes de wait, lo limpia en finally; cancel lo lee y mata OK
Backoff interrumpible _wait_or_stop reemplaza time.sleep en retry path OK
Snapshot en add, no releer YAML Sí, en pq/queue.py::enqueue_run; worker reconstruye Pipeline desde meta.json OK
Ciclo: rota la cola en bucle infinito cycle.next_due_pipeline con cycle_idx en memoria + auto-enqueue via queue.enqueue_run OK
Ciclo respeta cooldown y quota Sí, _pipeline_name_is_due chequea ambos antes de despachar OK
Ciclo + add manual coexisten en FIFO Sí, ambos terminan en la misma tabla y pick_next_run ordena por id ASC OK
Recuperación ante daemon crash No hay sweep de runs "running" huérfanos; quedan colgados GAP
Lock entre daemon y pq add simultáneos SQLite tiene su propio lock; no hay problema mientras no haya escrituras largas concurrentes OK (en la práctica)
Quita runs viejos / basura No hay gc; la tabla runs crece sin límite GAP menor

En resumen: lo que pediste está hecho y testeado. Hay dos huecos pequeños (daemon crash + falta de GC), pero no afectan al caso de uso del ciclo. Si quieres cubrirlos, lo planeamos aparte — son ~30 min de código cada uno, no arquitecturales.
